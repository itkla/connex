# Backend — Agent Guide

The root [`/AGENTS.md`](../AGENTS.md) applies here in full. This file adds backend-specific rules. The Golden Rules — Explore→Plan→Question→Act, match existing patterns, docs-only comments, strict null/type safety, layered architecture, and independent risk-tiered review — are not optional here.

## Stack

Spring Boot 4 on **Java 26** · MyBatis · Flyway + MySQL · Spring Security with **WebAuthn** · Lombok · JUnit 5. Multi-tenant, RBAC-enforced. Package root: `ooo.klae.connex.backend`.

Layout: `controllers/` · `services/` · `mappers/` (+ XML in `resources/mappers/`) · `dto/` · `beans/` · `tenant/` · `notifications/` · `businesscard/` · `config/` · `exceptions/`. Migrations in `resources/db/migration/`.

## Architecture — keep the layers clean

**controller → service → mapper.** Strictly.

- Controllers: HTTP only — validation, mapping DTOs, delegating to services. No business logic.
- Services: business logic and transactions. The only layer that calls mappers.
- Mappers (MyBatis): all data access. No SQL anywhere else.
- Cross-cutting tenancy and RBAC are load-bearing — every query must be tenant-scoped, every endpoint RBAC-checked. There are arch tests guarding this (`architecture/RbacEnforcementArchTest`, `tenant/TenantScopeInterceptorTest`); keep them green.

## Tenant isolation & RBAC — the core invariant

This is the most load-bearing property of Connex. A change that leaks data across tenants or bypasses RBAC is a critical defect, full stop. The detailed model lives in [`../docs/MULTITENANCY_PLAN.md`](../docs/MULTITENANCY_PLAN.md) — read it before touching tenancy.

- **Every query is tenant-scoped.** Reads and writes must be constrained to the resolved workspace/tenant. Most tables carry a workspace column (see the `*_workspace` migrations) — filter on it in the mapper, every time. Never trust a tenant id from the request body; use the resolved tenant context.
- **Never join across the catalog plane wall.** Org-wide control workflows that need tenant data must load a complete control-plane workspace ID/name allowlist, install `TenantWorkScope` before invoking a separate proxied transaction bean, and pass that allowlist into the tenant mapper. Keep control lifecycle and audit-log SQL in a control mapper, tenant content SQL in a scoped mapper, and hydrate control labels after the tenant read. `DataSubjectRequestService` is the reference orchestration pattern.
- **Every endpoint is RBAC-checked.** No controller method is reachable without the appropriate role/permission check. Mirror how the neighboring controller for the same entity authorizes.
- **Don't disable the guards.** The tenant-context enforcement and `TenantScopeInterceptor` exist to fail closed when no tenant is resolved. Don't switch them off to "make it work."
- **Keep the arch tests green:** `architecture/RbacEnforcementArchTest` and `tenant/TenantScopeInterceptorTest`. If a change requires touching them, that's a signal to stop and re-think, not to edit the test.
- Sharing/permissions changes get extra scrutiny and a `/security-review`.
- **Enroll every org-data table in tenant lifecycle.** A new entry in `TablePlaneRegistry.ORG_DATA_TABLES` must also have one exact `TenantLifecycleRegistry` declaration so export, teardown, and residual verification cannot drift. A mapper that reads `person` must be assessed in `ProcessingRestrictionRegistry`; the lifecycle and APPI architecture tests enforce both obligations.
- **Lifecycle routing is privileged cleanup only.** Ordinary `TenantWorkScope` resolution rejects a workspace or organization in `tearing_down`. Only deletion retry, startup reconciliation, and tenant teardown may use `inLifecycleWorkspace`; never use it to admit ordinary reads or writes around the lifecycle fence.

## Security & secrets

- **Never log secrets or PII** — no passwords, tokens, session ids, WebAuthn material, or personal contact data in logs or error messages.
- **Never commit credentials.** Database passwords live in local env/config, not source control. For local Docker MySQL, create `backend/.env` from `backend/.env.example`, fill throwaway local passwords, and keep the file untracked.
- **Validate all input** at the boundary (`@Valid` + Bean Validation on DTOs). Treat request data as hostile.
- **Auth/WebAuthn** flows are sensitive: don't weaken session handling, CSRF, or credential verification to simplify a change.
- **Authenticated session generations are opaque.** Every authentication method must continue through `AuthService.establishAuthenticatedSession`, which rotates the servlet session and the non-authorizing opaque `requestIdentity` returned by `/api/auth/csrf`; never return a principal id or servlet session id for client-side request correlation.
- Prefer parameterized MyBatis (`#{}`) over string substitution (`${}`) to avoid SQL injection.
- Business-card uploads accept only bounded, fully decoded JPEG/PNG/WebP bytes. Business-card and managed-image decoders share `ImageDecodeAdmissionService`; preserve its global decode-slot and estimated working-memory admission, pre-decode sample-depth/channel checks, and metadata-free canonical re-encoding through the seek-capable capped output so oversize encodings are refused before allocation. The OCR sidecar is private and bearer-authenticated; never log card bytes or recognized contact text, and never make runtime OCR model downloads or remote-image fetching possible. Outside `dev`, use HTTPS or explicitly bind plaintext OCR transport to a single-label service with `CONNEX_OCR_PLAIN_HTTP_PRIVATE_HOST` on an isolated private network. Local PaddleOCR remains the preferred scan path. Scan-time fallback decisions must join or start the bounded `CONNEX_OCR_LOCAL_FIRST_WAIT` readiness probe before treating Paddle as unavailable; availability polling stays non-blocking. When Paddle is unavailable, only an actor with `AI_USE` may send the metadata-free canonical JPEG through the organization's configured provider; the shared `AiInputImage` boundary enforces the conservative multimodal byte/dimension envelope, readiness accepts only verified image-capable model families and exact supported Vertex model/location pairs, the exact resolved provider snapshot is rechecked before egress, and provider adapters embed bytes directly rather than supplying fetchable URLs. Scan entitlement, workspace permissions, and principal/global admission must run in the security filter before multipart parsing. Confirmed imports require a caller-retained UUID `Idempotency-Key`; validate it, check workspace permissions, and principal-throttle it in the same pre-multipart filter, then keep tenant/reservation validation in `BusinessCardService`. Claims, request fingerprints, and result IDs stay workspace-scoped in `business_card_import_request` so retries cannot create duplicates or replay a different payload. `created_by_user_id` is non-null and ownership checks fail closed. Reserve and status admission precedes mapper access; status uses the nonlocking read.
- Connected capture is a fail-closed provider-egress boundary. Connection availability, global scheduling authorization, and each provider's ingestion authorization are separate flags and all capture flags default off. Preserve the provider-neutral adapter contract, fixed-host redirect-free bounded transport, generation/lease-safe token refresh, no provider I/O inside database transactions, tenant-routed page commits, exact-only canonical matching, inert backfill projection, immediate policy pause, and purge-before-credential-destruction order. Never log tokens, source content, identities, subjects, bodies, or raw provider responses. The supported data envelope, operator gates, privacy exclusions, support boundary, and deletion/export/incident contract live in [`../docs/CONNECTED_CAPTURE.md`](../docs/CONNECTED_CAPTURE.md).

## Data, migrations & MyBatis

- **Schema changes go through Flyway.** Add new migrations under `db/migration/tenant/` (org-data tables only — the future per-org catalog lineage) or `db/migration/control/` (control-plane tables only). Name versioned migrations `V{next}__{snake_case_description}.sql` with the next sequential number after the highest existing `V` across ALL migration folders; reserve `R__{snake_case_description}.sql` for definitions that are intentionally repeatable. The interleaved V1–V65 root lineage is frozen history. Rebase before merge and renumber every unmerged migration that no longer exceeds the latest `main` maximum; CI compares additions with the pull request base across the single global sequence. `MigrationLineageArchTest` enforces purity against `TablePlaneRegistry`, and `TablePlaneArchTest` requires every new table to get an explicit plane placement; no foreign key may cross the plane wall in either direction — replace it with service-layer validation (`UserOffboardingService` is the pattern). Never edit or renumber an applied migration. Make migrations forward-only and mind MySQL specifics.
- **Pin the collation on `VARCHAR` columns used in a composite foreign key.** A `CREATE TABLE` with no explicit charset/collation inherits the database's *current* default, which drifts between environments (a long-lived catalog created under `utf8mb4_unicode_ci` versus a fresh one on `utf8mb4_0900_ai_ci`). A composite FK whose string columns end up with mismatched collations is rejected by MySQL (errno 3780) and — because DDL auto-commits — half-applies and leaves Flyway wedged. CI never catches it (its scratch catalog is uniformly `0900`), so it only surfaces on a legacy DB. Declare `CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci` explicitly on the parent key column and every referencing child column (see `V114__saved_view_record_type_collation.sql`).
- New tenant-scoped tables need their workspace column from day one — follow the `*_workspace` migrations as the pattern.
- **MyBatis mappers:** Java interface in `mappers/`, XML in `src/main/resources/mappers/{Entity}Mapper.xml`. Mirror an existing mapper pair. All data access lives here — no SQL elsewhere. Use `#{}` bindings.

### Workflow principal and lifecycle lock order

Workflow lifecycle writes and permanent account offboarding use one lock hierarchy: discover identity-bound keys without locks; lock every referenced `app_user` root in ascending user id; lock candidate workspace roots in ascending workspace id (`FOR SHARE`, or the existing stronger owner lock); lock required `workspace_member` rows in ascending user id; lock the actor's custom `workspace_role` root and exact permission row when current authorization depends on it; then lock exact workflow, workflow-version, and rule point keys in that order. Version and rule key discovery must be non-locking and Java-sorted before individual `getByIdForUpdate` calls—`ORDER BY ... FOR UPDATE` is not a lock-order guarantee. Revalidate the exact locked rows before writes. Final workflow authorization must use the locked membership's current `role` and `role_id`, never a pre-lock `WorkspaceService` permission snapshot. Account offboarding must take the union of owner and workflow workspace roots in one ascending pass before membership rows, then disable affected paired and unpaired rules before redacting nullable principals.

Built-in and custom workspace-member role mutations follow the same roots: after preliminary authorization, lock the actor and target `app_user` roots in ascending id order, the exact workspace exclusively, and the actor and target memberships in ascending user id order. Revalidate the actor as active and the target as `active` or `pending`; final authorization must use that locked actor membership, never the earlier permission snapshot. Lock all distinct actor-custom and requested-custom `workspace_role` roots in ascending id order, then read their complete permission sets with ordered locking reads before checking current permission and grantability. Owner demotion locks the exact workspace's owner rows while that workspace root is already held; it must never reacquire the broader owned-workspace root set. Custom-role creation uses the actor half of this protocol before insertion; update and deletion additionally lock the exact target role before changing its name, permissions, assignments, or cascade state. Pending-membership approval locks the user root, exact workspace exclusively, and exact pending membership before domain validation and activation. The exclusive workspace root serializes these paths with workflow lifecycle's shared workspace root.

Lifecycle, APPI data-subject request, and organization SSO control writes share one global root order: discover without locks; lock referenced `app_user` roots in ascending id; lock workspace or cleanup-tombstone roots in ascending workspace id without joining the organization; lock the organization; lock exact `org_member` rows in ascending user id; then lock operation rows. Revalidate every locked root before side effects. APPI creates and updates perform preliminary subject-workspace and person validation outside the write, then retain the actor user, every previous/requested subject workspace root in ascending order, and the organization shared lock while locking the requested tenant person; an initially missing, inactive, or foreign workspace or missing person is a bad request, while person loss, workspace loss, or lifecycle fencing after preliminary proof is a conflict. Linked mutations serialize a non-auto-commit tenant-connection reservation before taking control locks, prove the person through a separate short session while the reserved session remains SQL-idle, then use the reserved session plus one control transaction; the final control write joins the root-lock transaction, so the person lock remains held through its commit without a third pool checkout. The reserved transaction is rolled back before release. Retaining the control roots before the person lock prevents account-offboarding lock inversions. Updates lock the exact organization-scoped request `FOR UPDATE` after the roots and compare every persisted field with the preliminary snapshot before deriving the diff or writing. Returning and existing-user SSO paths discover nonlocking, then lock the user, stored workspace when applicable, and organization before revalidation; new JIT paths with no user row lock the stored workspace and organization before revalidating absence and inserting.

The legacy `/api/rules` write surface is a compatibility projection, not an independent aggregate. Every create must transactionally create its paired workflow and immutable version 1. Every update discovers and locks the complete pair through the hierarchy above, preserves the active user-mode run-as identity, creates no version for a semantic no-op or enabled-only change, and creates exactly one deterministic legacy graph/canvas version for a semantic change. Delete is archive-only: disable the retained rule, set the paired workflow's `archived_at`, and retain every version, canonical run, step, rule execution, and legacy link. Restore clears `archived_at` and leaves both runtime surfaces disabled. Startup backfill follows the same hierarchy: non-locking Java-sorted discovery, sorted principal roots, the workspace root exclusively, exact workflows, exact active versions, exact rules, then a final locking rule enumeration that proves completeness before inserts or verification.

Canonical workflow execution pins one immutable `workflow_version` in `workflow_run` and commits one node side effect plus its `workflow_step_run` checkpoint per `REQUIRES_NEW`, `READ_COMMITTED` transaction. Every resume reloads the pinned version, verifies its definition hash, and revalidates actor membership, record visibility/restrictions, and action permissions before mutation. A later permission, membership, record, or reference failure becomes fixed-code run evidence; it is never converted to a silent skip. Disable and archive stop new claims but do not cancel a claimed run. `runtime_owner` on the locked workflow is the database-authoritative legacy/canonical predicate; both engines check it and the opposite ledger under the same root lock. The deployment gate defaults off until the durable V144 runtime is installed everywhere. Keep `WorkflowTriggerIntake`, the compiled graph, run/step beans and mappers, and traversal services extensible for the outbox, leases, waits, attempts, and cancellation checks; do not reconstruct traversal from flattened version metadata.

### Task mutation lock order

Task creation and full update lock the requested active `workspace_member` first, matching offboarding's membership → task order. Every mutation that can change board positions runs at `READ_COMMITTED` and fails closed if it joins a transaction with any other isolation, then acquires the exact tenant-plane `task_board_lock` row for the workspace through the atomic insert-or-update mapper statement. Any transactional caller that wraps a task-board mutation must therefore declare the same isolation. Creation follows membership → board root → insert; full update follows membership → board root → exact task rows; completion, deletion, and movement follow board root → exact task rows. Due-date-only rescheduling remains an exact-task mutation and never acquires the board root. A full update that changes `completed` must authorize the transition against the assignee on the locked pre-update task, not the requested assignee.

After holding the board root, discover workspace task ids without locks, add the requested root id, Java-sort the union, and lock each exact `(workspace_id, id)` key individually through `getTaskByIdForUpdate`. Skip siblings that disappeared before their exact lock, fail closed when the requested root disappeared, and derive source and target order only from the current locked rows. Creation appends while holding the board root; completion, reopening, deletion, and movement compact every affected status column to contiguous zero-based positions before commit. Never substitute an `ORDER BY ... FOR UPDATE` range scan or return to nonlocking board reads after waiting for the exact locks.

### Import duplicate review and lock order

Person and company duplicate review has one boundary: `DuplicatePreflightService` normalizes every identity and name with `MatchingService`, hydrates the same-organization workspace allowlist through `OrganizationWorkspaceScopeControlAccess`, and then calls the visibility-scoped `IdentityMapper` reads. Strong evidence is exact canonical email, phone, domain, or external ID; weak evidence is exact normalized name after a bounded broad candidate read and Java recheck. Never auto-attach an unreviewed weak, shared, ambiguous, truncated, or aggregate-overflow result. Direct responses contain at most 50 candidates; CSV responses contain at most 8 per row and 1,000 across the request. Preview admission stores only SHA-256 workflow, raw-payload review-context, and ordered-result fingerprints plus a random, one-use rendered-review proof; never retain normalized PII. The server-derived review context binds workspace, rows, mapping, duplicate action, and manual links before matching begins. Every person, company, and deal CSV commit atomically claims the exact unexpired proof returned by its preview before acquiring database locks, even when the duplicate result is empty. A failed preview must cancel its reserved proof.

Manual person/company creation, staged contacts, and OCR-reviewed contact and company creation must all submit their current fields through this boundary. Client debounce is presentation only: the client rechecks immediately before mutation, binds any acknowledgement to the exact request workspace plus the complete candidate-response token, and cannot acknowledge a truncated response. Candidate-affecting creates, updates, restrictions, deletes, person/company share changes, imports, OCR, and identity backfill lock through `DuplicateDecisionLockService` before any record or identity lock. Request transactions use `READ_COMMITTED` and acquire the actor user, every active workspace root needed by the mutation in ascending id, required active memberships, the active organization shared, then the dedicated organization duplicate-decision mutex exclusively; principal-free backfill starts at its active workspace. Person/company sharing retains both source and target workspace roots before the mutex. The shared organization root fences lifecycle teardown while the dedicated mutex serializes the complete same-organization visibility domain without inverting ordinary tenant-row → audit-organization locking. Target locks follow in ascending record ID, then canonical identity groups in deterministic kind/value order. OCR acquires the hierarchy before its first persistence read so final rechecks use the post-lock snapshot and identity provenance remains `BUSINESS_CARD`.

Person, company, and deal CSV commits acquire the duplicate-decision hierarchy before commit-time matching. Person and deal previews include every exact referenced-company name in the same proof; deal proofs additionally bind every rendered create-vs-match decision. A unique visible company dependency may be reused, no match may be created under the held duplicate mutex, and ambiguous or truncated dependencies fail closed only for rows that will consume them. Commits then lock every writable matched target individually in ascending record ID and all supplied canonical identity groups in deterministic kind/value order. Requery current identities while holding those locks: automatic targets must remain the unique owner of the supplied identities, and creates must still have no owned match. Only then may the commit create custom-field definitions, tags, or reviewed referenced companies. A vanished target invalidates only its rows; unrelated valid rows continue, and an all-vanished batch produces no dependency or audit side effect. Dependency creation uses stable canonical-key order after target and identity locking. Do not introduce a dependency-first lock pass: ordinary record mutation is duplicate-mutex then target-first, and reversing it creates an interactive/import deadlock cycle. Any dependency that disappears after resolution must fail through transactional revalidation or foreign-key enforcement so the complete import transaction rolls back.

Interaction-history CSV commits use the same one-use proof and duplicate-decision hierarchy, lock resolved people in ascending order, and write activities, notes, or tasks in bounded direct mapper batches with replay provenance. Source-less rows receive their stable semantic-occurrence ordinal before participant resolution so progressive manual linking cannot renumber them; legitimate identical interactions stay distinct while replaying the same ordered file remains idempotent. They must never call per-row service, rule, mention, audit, or notification publishers. Historical notification baselines are computed independently of delivery preferences and may suppress only expectation keys causally scoped to the imported people, their changed deal-risk expectations, or exact imported task IDs at one fixed evaluation instant. A disabled recipient preference retains its baseline, and an import-caused deal-risk disappearance retains the existing reminder until a live source-state change. Compare the pre-import snapshot with a post-write counterfactual that excludes the exact imported entity IDs and fail the transaction when relevant non-import inputs changed concurrently. Bind each baseline to a content fingerprint over the complete persisted source evidence, applying the same exact import exclusions to the counterfactual, so a later live source change releases it even when notification severity stays constant; do not bind it to clock-only decay or presentation fields. Advance an existing baseline only when it still matches the pre-import stable source state. Baselines are tenant lifecycle data and must be removed beside recipient notifications during fresh-membership cleanup, member detachment, invitation decline, and account erasure.

## Private object storage

Attachments, contact pictures, company logos, user profile pictures, and business-card source images are stored by the backend through `ObjectStorage`; never write uploads into the frontend image or public directories. Managed object URLs are opaque authenticated backend endpoints, not public filesystem paths. The default local provider writes under `${user.home}/.connex/object-storage`; the deployment bundle mounts `/var/lib/connex/objects` from its durable `object_data` volume. Filesystem writes reserve their declared size against `CONNEX_OBJECT_STORAGE_FILESYSTEM_MIN_FREE_BYTES`, and storage readiness fails when that floor cannot be preserved. Startup and scheduled reconciliation remove only expired `.connex-object-*.tmp` files without following symbolic links; retention and cadence are configuration properties and failures must be logged. The first configured backend identity is immutable control-plane state: provider plus normalized filesystem root or all S3 addressing coordinates. Every startup must insert-or-verify the singleton and abort on mismatch before filesystem reconciliation or storage readiness probing. Set `CONNEX_OBJECT_STORAGE_PROVIDER=s3` plus the bucket and region settings documented in [`../docs/DEPLOYMENT.md`](../docs/DEPLOYMENT.md) for S3-compatible storage.

Metadata replacement and removal must enqueue the old object in a durable deletion queue in the same database transaction; the bounded background reconciler performs provider I/O after commit so request commits never block on S3 or filesystem deletion. Its two-thread bounded executor keeps provider latency off the shared scheduler and isolates control-plane retries from tenant-plane retries; overlapping scheduled sweeps coalesce instead of queuing. Tenant-owned keys use that catalog's `object_deletion_queue`; control-plane user-profile keys use `user_object_deletion_queue`. Profile-image replacement must hold the user-row lock before shared backlog admission and the object write. Before provider I/O, persist a delayed two-pass cleanup tombstone in an isolated transaction, then lock and revalidate that exact id/key in the metadata transaction before quota and provider work; cancel only the exact locked identity after the provider confirms the write. Retry workers must lock the selected id/key and recheck due state before deletion so stale selections cannot delete newly committed bytes. Tenant cleanup sweeps rotate their per-catalog workspace cursor and reserve an initial fair slice for every selected workspace before redistributing spare capacity. Preserve the deletion-queue → quota → audit lock order, including storing business-card binary bytes before company/person/audit writes. This ordering covers rollback, process exit, and ambiguous provider failure. For S3, both the initial tombstone delay and the delay between delete passes must exceed the two sequential call timeouts for the versioning preflight plus the object operation; never replace the tombstone with a direct or single immediate delete that can race a late provider write.

Managed response streams must pass through `ManagedObjectReadAdmissionService`, which holds global and authenticated-user permits until close or the hard deadline. Its timeout scheduler has exactly the global concurrent-read limit in workers so one blocked provider close cannot stall another admitted deadline. Keep the MVC streaming executor bounded to the same global limit. Filesystem readers hold a per-path lease through stream close; deletion must fail and remain queued while a reader owns that lease so physical bytes and quota accounting cannot diverge. Lease acquisition and release can occur on different request, streaming, and timeout threads, so the lease primitive must not depend on thread ownership.

Tenant export admission is database-global and has one application/schema invariant: capacity is between 1 and `MAX_CONCURRENT_EXPORTS`, currently 4. In one control transaction, lock the actor user shared, the exact workspace shared, the organization shared, and the exact actor organization membership exclusively before taking the singleton export-admission row with `FOR UPDATE NOWAIT`; validate the locked capacity, count every committed export lease globally, and insert the exact durable token only below capacity. Capacity or singleton contention returns immediately with HTTP 429. Capture every registry table cursor and the distinct active-object reference stream in one read-only repeatable-read transaction; table JSONL goes directly to the ZIP and object references go to a synchronously created owner-only `0600` spool. Close every cursor and the database transaction before provider I/O, then export exactly the captured objects and fail closed on any missing or mismatched metadata, ledger, URL, owner, key, or byte length. The manifest remains last. The monotonic export deadline only signals one deduplicated cancellation worker; servlet timeout, error, and completion callbacks never block on resource close. Cancellation force-aborts the exact snapshot JDBC connection and confirms connection closure; never rely on `Statement.cancel()` or `Statement.close()` to interrupt a Connector/J streaming cursor. Cleanup attempts every tracked non-lease close and spool deletion, clears the spool reference only after successful deletion, and releases the exact export lease last only when all non-lease cleanup is certain. Output, provider, cursor, spool, or cancellation-dispatch uncertainty retains the durable lease. A persisted lifecycle operation lease never ages out or gets reaped automatically: teardown must refuse immediately while any applicable lease row remains, and operator cleanup is permitted only after independently proving that no export still owns it.

Tenant-owned object admission must reserve exact key and byte usage through `WorkspaceObjectStorageQuotaService` in the metadata transaction. Release that reservation only after physical deletion succeeds; bypassing the ledger makes workspace quotas raceable or permanently inaccurate.

Tenant teardown must preserve workspace placement and storage ledger rows until every enumerated object is physically deleted through `ObjectDeletionRetryQueue`. A provider failure leaves the lifecycle root and retry state intact; only a clean registry-driven residual scan permits control-root deletion.

Legacy public-upload migration is an explicit non-web maintenance command, never a normal server startup mode. Preserve its control-plane workspace enumeration plus `TenantWorkScope.inWorkspace` routing, deterministic replay-safe object tokens, read-after-write integrity check, compare-and-set metadata rewrite, source-file retention, dry-run quota projection, and exact apply confirmation. The operator sequence lives in [`../docs/DEPLOYMENT.md`](../docs/DEPLOYMENT.md); migration mode must default to `off`, require the centralized startup validator's exact `connex.maintenance.mode=legacy-upload-migration` plus `spring.main.web-application-type=none` pairing, and keep schedulers, async execution, bootstrap, and secret-rewrap runners absent from that application context.
Normal web startup still performs a metadata-only, fail-closed count of all four retired public URL prefixes across control and routed tenant catalogs. It must never read or migrate legacy bytes, and any remaining reference or unservable catalog aborts startup. The deployment readiness marker is published only after all `ApplicationRunner`s complete; production Compose waits for backend health before it may recreate the frontend, and upgrade runbooks start Caddy last so old writable-layer media cannot be destroyed before the guard succeeds.

Connex disables Spring JNDI property-source discovery through the classpath `spring.properties` policy before either packaged or external-WAR startup creates an environment; datasource JNDI is not a supported configuration channel. Seeder startup must use the dedicated `SeederApplication` launcher, which sets `WebApplicationType.NONE` before environment creation. A separate ConfigData-aware environment post-processor runs at `Ordered.LOWEST_PRECEDENCE - 1`, immediately before the database-transport processor and before datasource/Hikari/Flyway/MyBatis/JDBC/JNDI or operator class construction. Any genuine seeder signal requires both that pre-binding application type and the defense-in-depth `spring.main.web-application-type=none` property, so the executable `BackendApplication` and external-WAR `ServletInitializer` paths refuse seeder mode. The activated contract also requires `seeder` as the only profile, exact seeder enablement and maintenance mode, single-database routing, an unset deployment profile, legacy upload migration off, and a simple MySQL baseline target. Keep seeder configuration closed: raw `hikaricp.configurationFile`, alternate/routing JDBC forms, unknown Connector/J query or map properties, Hikari class/JNDI/XA/object/catalog/schema/test-query channels, and Spring application sources and initializer/listener classes are refused. The complete relaxed `spring.flyway`, `spring.sql.init`, and `mybatis` namespaces are closed. Flyway operator configuration is allowed only for the already-validated dynamic target channels `url`, `driver-class-name`, `jdbc-properties`, `default-schema`, and `schemas`; separate Flyway credentials and every other operator Flyway property are refused, including same-value overrides, relaxed aliases, indexed/descendant forms, removed or deprecated names, and unknown future names. `application-seeder.yml` must be the effective source for the current Boot 4.1/Flyway 12 migration semantics: migration enabled; baseline-on-migrate at version `0`; clean disabled; migration execution not skipped; target `latest`; history table `flyway_schema_history`; default resolvers and callbacks enabled; exactly `classpath:db/migration`; empty callback locations and init SQL; an absent closed placeholder namespace whose bound default is empty; empty ignored migration patterns; placeholder replacement off; `V`/`R` prefixes, `__` separator, and exactly `.sql` suffixes; validation and migration-name validation on; out-of-order off; and missing locations fatal. The SQL initializer and MyBatis pins remain repository-owned, and every operator override, alias, indexed value, executable class channel, and unknown descendant is refused even when its value matches a pin. Connector/J option names match reviewed canonical names and explicit compatibility aliases case-insensitively but do not use Spring's punctuation-relaxed matching. `connectionAttributes`, `clientCertificateKeyStoreUrl`, and `trustCertificateKeyStoreUrl` are explicitly refused, together with certificate-store passwords, in JDBC query, Hikari map, and Flyway map forms; remote TLS may use only JVM/system trust material, never per-connection keystore URL hooks. Add a Connector/J option only after reviewing it as inert/TLS/timeout/encoding/timezone/performance configuration and extending the characterization tests; never replace the closed allowlist with a blacklist. Repository-owned Java Flyway callbacks, migrations, and customizers remain allowed.

## Conventions

- **Comments:** Javadoc on classes/methods only. **No inline comments.**
- **Null/type safety:** validate DTOs (`@Valid`, Bean Validation); guard nulls; no unchecked casts. Prefer explicit handling over silent fallthrough.
- **Use Lombok** as the existing code does; don't hand-write boilerplate it generates.
- **Error handling:** throw the domain exceptions in `exceptions/` (`BadRequestException`, `ForbiddenException`, `ResourceNotFoundException`, `DuplicateResourceException`); `GlobalExceptionHandler` maps them to HTTP responses. Don't build ad-hoc error bodies or catch-and-swallow.
- Mirror the existing controller/service/mapper for the entity you're touching before adding new patterns.

## Smart segments & the condition model

Smart-segment evaluation lives in `SegmentService` as a reusable **condition model**: a `SegmentDefinition` (`match` = `all`/`any` over `SegmentCondition`s), where each condition is a graph-aware **predicate** (`warm_intro_available`, `open_deal`, `cooling`, `no_activity`) or a **field** comparison (`industry`/`name`/`tag`), optionally negated — evaluated to workspace + current-user-scoped record ids via `SegmentMapper`. This model is deliberately feature-agnostic: the planned **rule engine (#54)** should consume it as its `WHEN` rather than inventing a new condition language (segments are state-matching; rules add the transition/trigger + action layer on top).

The vocabulary is declared **once** in `SegmentCatalog` (a `@Component`): the supported record types, each field's `Kind` + `ValueSource` + legal operators, each predicate's applicable record types + `days` bounds, the enum option sets, and the definition shape limits. `SegmentService` consults it for validation and evaluation dispatch, and `GET /api/segments/catalog?recordType=` serves it to the client (workspace-independent + cacheable; the workspace value options — tags, industries, owners, stages — stay on the separate `/fields` endpoint). **Add a new field/predicate here** (`SegmentCatalog` entry + `SegmentMapper` query, every statement `#{}`-bound and workspace-scoped) — the frontend renders it generically, needing only i18n label keys in `messages/en` + `messages/ja`. Keep the catalog **additive** (never rename/remove a key: persisted definitions in rules/campaigns must keep validating; a broken key silently kills a rule via the engine's catch-and-log). Predicate applicability is company-only today; when generalizing to person/deal (epic #616), the "Predicates are only available for company records" message becomes per-key. `Kind` is a closed enum on both ends — a new kind is a deliberate frontend change, not a catalog-only one.

## Rule engine

Automation rules and canonical workflows layer a trigger + actions on top of the segment condition model. Conventions:

- A rule = **trigger** (`entity_change` after-commit events, or a `schedule` cadence) + optional **WHEN** (a `SegmentDefinition`, company-only today) + **THEN** actions. Trigger/condition/actions are JSON columns, validated per type in `RuleService`.
- **Execution identity.** A rule runs as the run-as member (`user` mode) or the global system actor (`system` mode, gated to admin via `requireRole(ADMIN)` at authoring). `SystemActor` is a seeded non-login user (migration `V20`) whose permissions are a fixed narrow set granted in `WorkspaceService.permissionsFor` — extend that set if you add an action needing a new permission. Off-thread execution installs SecurityContext + TenantContext via `AutomationExecutor`, so the existing tenant- and RBAC-enforcing services apply unchanged; an actor lacking a permission fails the action.
- **Adding a trigger event.** Emit it after the mutation's write via `ruleTriggers.publish(workspaceId, recordType, entityId, "<entity>.<event>")` (alongside any `notificationChanges.publish`) from the same transaction, and add the token to the rule's validated vocabulary. `WorkflowTriggerIntake` inserts one bounded target per matching workflow before commit; the fair runtime scheduler drains those rows after commit. A mutating source service without a transaction must not publish a trigger because `Propagation.MANDATORY` intentionally fails the mutation instead of recreating an after-commit loss window.
- **Adding an action.** Add the type to `RuleService` validation and a branch in `RuleActionExecutor` (delegating to the existing service), and grant any new permission to `SystemActor` if `system` mode must perform it.
- **Idempotency and ownership.** One replay-stable trigger envelope derives the same bounded SHA-256 dedupe key for both ledgers. Legacy claims use `rule_execution`; canonical claims use `workflow_run` with uniqueness on `(workspace_id, workflow_id, dedupe_key)`. Both claims lock the paired workflow, require their persisted `runtime_owner`, and check the opposite ledger before insertion. Schedule keys use a UTC cadence bucket. Never derive replay identity from process time or a JVM-local owner flag.
- **Schedule enrollment.** A schedule Trigger immediately targets one Condition. That Condition selects records before run creation, enrolled runs record it as `yes`, and its `no` edge is never traversed. Later Conditions branch normally. Entity-change runs evaluate every Condition normally.
- **Durable execution.** `workflow_trigger_outbox` pins workflow generation and version at source commit. `workflow_runtime_workspace` serializes fair alternating trigger/run claims per workspace; UUID owners, database-time leases, `SKIP LOCKED`, and owner-fenced checkpoints make stale multi-instance workers harmless. Publish, enable/disable, archive, and restore advance `runtime_generation`, invalidating pending intake without cancelling existing runs. Delay and retry waits release their lease and resume through the same due-run claimant.
- **Cancellation and retry.** Queued and waiting cancellation terminates immediately; running cancellation is cooperative and checked before every node effect. An action attempt is reserved before effect execution, while the database mutation, attempt/step success, and next-node checkpoint commit together. Automatic retry is limited to transient lock/serialization/query-timeout failures and actions classified by `WorkflowActionRetryPolicy`; every unknown action defaults to `none`. Database-backed schema-v1 actions are `transactional`, while `notify` is `deduplicated` by `workflow:{runId}:node:{nodeId}`.
- The engine runs **off the request thread** — pass `workspaceId`/`userId` explicitly to mappers and to the session-free `SegmentService.evaluate(workspaceId, userId, …)`; never rely on the request's tenant context there.

## AI subsystem (BYOP) — the masking boundary is load-bearing

The AI foundation (issue #94; packages `ai/`, `ai/masking`, `ai/provider`, `ai/egress`, `ai/brief`) is customer-BYOP and **fail-closed per organization**. Provider configuration supports Amazon Bedrock, Azure OpenAI, Vertex AI, and OpenAI-compatible endpoints; all four providers are adapter-ready. `connex.ai.enabled` defaults false pending live public/APPI disclosures and counsel approval, so an instance operator must explicitly opt in with `CONNEX_AI_ENABLED=true`. Each entry under `connex.ai.features.*` defaults on when absent and can disable one feature independently, but the master flag still disables all features. Even when both switches permit a feature, `AiFeatureGate` denies the call unless it also finds the actor's `Permission.AI_USE` plus a per-org provider config (`ai_provider_config`) that is enabled, no-training-attested, adapter-supported, complete for its provider, and credentialed when that provider requires credentials. Credential bundles are envelope-encrypted via `SecretPurpose.ORG_AI_PROVIDER_CREDENTIAL`; OpenAI-compatible endpoints may be unauthenticated. Editing provider settings is org-admin + step-up gated (`OrgMemberService.requireOrgAdmin` + `requireRecentAuthentication`), mirroring SSO config.

Rules for any new AI-powered feature:

- **Every model call goes through `AiInvocationService.complete(...)`** — never call `AiProvider`/`BedrockClient` directly. That choke point enforces the gate, credential resolution, the outbound leak scan, demasking, and the metadata-only `ai.llm.call` audit (attempt/success/failure/blocked; never prompt, response, or credential content). Embedded media additionally holds `AiMediaAdmissionService` global, per-organization, and estimated-memory leases through provider parsing. Preserve the OpenAI-compatible and fixed-provider transports' hard wall-clock cancellation, bounded resolver pools, and pinned final addresses; a response/socket inactivity timeout alone does not stop slow-drip endpoints.
- **Cache-miss text generation goes through `AiInvocationAdmissionService`.** Its single-flight losers wait for the leader and then re-read persistent cache; collisions never become rate limits. Organization quotas, forced-refresh throttles, and active-flight state are bounded and per JVM replica, so cluster-wide enforcement requires a shared coordinator.
- **Interactive text generation uses the shared bounded handle contract.** Deal brief, deal risk rationale, introduction rationale, and report narrative initiation go through `AiGenerationService`; clients poll `/api/ai/generations/{handle}` rather than holding a provider-latency HTTP request open. Keep the registry single-node, opaque, size/time bounded, exact-user/workspace scoped, and capacity-reserved before background work; global, workspace, and cross-workspace user retained-result limits must reject before any billable provider call. Status reads must revalidate current permissions, the AI restriction epoch, and the live feature gate before disclosing generated content. Background work reloads the principal and propagates `SecurityContext`, `TenantContext`, and locale through `AiGenerationContextRunner`, while feature services retain cache identity, quota, provider single-flight, masking, egress, and audit ownership. Carry the expected restriction epoch through the feature task, but acquire its atomic read fence only at provider egress; person-backed cache persistence acquires contributor rows after egress and must not run beneath that fence because restriction mutation takes person rows before the epoch write fence.
- **No feature builds raw prompts.** Tokenize identifiers with `MaskingEngine.maskField` (person/company names) and route ALL free text through `MaskingEngine.maskFreeText` (special-care screen + identifier substitution); assemble via `PromptAssembly`. `MaskedPrompt` is only constructible inside `ai.masking` — by design; do not widen its constructor. Emails/phones/addresses are excluded from text prompts (see `IdentifierPolicy`); `special_care` text data is always excluded. Sanitized image pixels cannot be masked or pre-screened like text: any image feature is an explicit media-policy exception that must use `AiInputImage`, a static prompt assembled through `PromptAssembly`, customer-facing disclosure, `AI_USE`, the no-training attestation, metadata-only audit, and review-only output.
- **Provider egress is validated and re-vetted.** Bedrock hosts derive from the closed `BedrockRegion` enum. Bedrock, Vertex, and Google OAuth use `FixedAiProviderClient` so bounded public-address resolution, address pinning, redirect refusal, and the HTTP exchange share one monotonic deadline; Vertex token and model calls share the same `AiRequestDeadline`. Azure OpenAI reconstructs HTTPS URLs from suffix-pinned `*.openai.azure.com` hosts and uses `AiEgressGuard.requireFetchableHost(host, false)` immediately before every send. OpenAI-compatible adapters may use the organization-configured HTTP(S) base URL, but must resolve through `AiEndpointAddressValidator` immediately before every send and honor `allowInternalEndpoint`; redirects remain disabled. Deployments with RFC 6052 network-specific translation prefixes must list them in `CONNEX_AI_NAT64_PREFIXES` so translated addresses are classified exactly; unclassified org-controlled IPv6 fails closed when any valid RFC 6052 interpretation could target blocked IPv4. New providers get their own adapter behind `AiProvider` and register through `AiProviderRouter`.
- **Degrade gracefully without hiding execution outcomes.** Gate/domain unavailability returns an explicit `available=false` result (for example `DealBriefDto.unavailable`), while the asynchronous contract reports provider failure, rate limiting, and timeout as distinct terminal states. Deterministic features (deal risk, warmth, and report figures) keep working without AI.
- The masking map is request-scoped and never persisted; masking reduces provider exposure but does not change Connex's APPI handler status (Connex can re-identify). Keep it that way — no token vault.

## Delegated backend work

Follow the root risk tiers and dispatch budgets. Backend depth must come from exact contracts, tests, and targeted independent review rather than a fleet of agents repeating the same mapper/service search.

The root execution-discipline rules control backend work: targeted local checks are the default, required CI owns the exhaustive suite, slow local execution without a failure signal is abandoned rather than diagnosed, and no side investigation begins without mapping it to an active acceptance or exit criterion.

Any implementation agent, including Codex, receives an approved plan before editing: scope/approach, exact REST contract (paths, DTOs, error cases, RBAC + tenant scoping), migration DDL with the orchestrator-assigned Flyway version, files per layer (controller/service/mapper/XML/tests), and a test plan.

- The orchestrator writes the plan for Tier 1 and most Tier 2 work. Do not run a separate read-only planning agent merely to echo it.
- Use a separate read-only planning pass for Tier 3 work, unresolved transaction/locking design, cross-plane data movement, destructive migrations, or a genuinely unsettled cross-layer contract.
- Keep one backend implementation owner. Split another mutating lane only when migration numbers, contracts, and file ownership are fixed and non-overlapping.
- Standard backend work receives one independent read-only review. Tier 3 work receives the root two-reviewer split: security/tenant concerns and correctness/concurrency/migration safety.
- Discovery, review, and verification agents are exempt from producing an implementation plan, but they still receive a narrow unique charter.

## Definition of Done (backend) — the verify loop is required

1. **Run a test server:** `./gradlew bootRun` (MySQL via `docker-compose up -d db`, see `docker-compose.yml` — db on `:3306`, adminer on `:9001`). For business-card scanning, also start the optional private sidecar with `docker compose --profile ocr up -d ocr`, use the same 32+ character `CONNEX_OCR_SERVICE_TOKEN` in both processes, set `CONNEX_OCR_BASE_URL=http://127.0.0.1:8090`, and enable the feature explicitly.
2. **Curl every changed `*Controller` endpoint** at `http://localhost:8080/api/...`. Confirm status, body, and — critically — auth, tenant isolation, and RBAC behavior with real requests. Protected endpoints need a session: `POST /api/auth/login` to obtain the `JSESSIONID` cookie, `GET /api/auth/csrf` for a CSRF token, then send both on mutating calls. Exercise an unauthorized and an other-tenant caller too — prove the request is *rejected*, not just that the happy path works.
3. **Write automated tests and run targeted verification locally.** Run every test added or changed by the diff and the directly implicated guard or integration tests with `./gradlew test --tests '<fully.qualified.TestClass>'`. Add more `--tests` selectors only when they protect an invariant touched by the change. Do not run bare `./gradlew test` on the shared development host; the required `Backend — build & test` CI job runs the complete corpus except under the root execution-discipline exceptions.
4. **Scrutinize intensely** for bugs and future failure modes: tenant leakage, RBAC gaps, null/edge cases, N+1 queries, transaction boundaries, migration safety and reversibility.
5. **Independent backend review — once per material diff (required).** For standard work, use one fresh **gpt-5.6** Codex context at **high** reasoning effort from `backend/`:

   ```bash
   codex exec -m gpt-5.6 -c model_reasoning_effort=high --sandbox read-only \
     "Independently review the backend changes on this branch (git diff against main). Try to refute the implementation against its acceptance criteria. Hunt for logic flaws, tenant-isolation and RBAC gaps, null/edge cases, transaction mistakes, injection, N+1 queries, and unsafe migrations. Report actionable findings with file:line and severity. Do not edit files."
   ```

   This is the standard independent adversarial review; do not automatically add a second generic `/code-review` run. Triage every finding rather than accepting it blindly.

   Do not repeat a completed review unless the reviewed diff changes materially. If the command or provider fails before producing a review, make one fallback attempt with another available fresh read-only context; do not debug reviewer tooling during product work.
6. **Tier 3 escalation only.** For auth/WebAuthn, tenant routing, RBAC/sharing, secrets/crypto, provider egress/sync, destructive data movement, money/approvals, concurrency/locking, or release-critical work, use `/security-review` for the security/tenant slot and one fresh **gpt-5.6/xhigh** Codex review focused on correctness/concurrency/migration safety. Do not add further reviewers unless the two disagree or a concrete high-risk question remains unresolved.

## Commands

- Run (local): load `CONNEX_DB_*` from your untracked `backend/.env`, then run `SPRING_PROFILES_ACTIVE=dev ./gradlew bootRun` — the `dev` profile (`application-dev.yml`) turns the session and workspace cookie `Secure` flags off so login works over plain-HTTP `localhost`, permits local plaintext DB transport, and supplies a local-only audit-integrity HMAC secret. Without it the fail-closed default (`Secure=true`) drops `JSESSIONID` over HTTP and non-dev startup requires `CONNEX_AUDIT_INTEGRITY_HMAC_SECRET` plus a `CONNEX_DB_URL` with `sslMode=VERIFY_CA` or `sslMode=VERIFY_IDENTITY`. The systemd-controlled local staging checkout at `/opt/connex-staging/backend` is special-cased for `localhost:3001` auth defaults and explicit loopback MySQL with `sslMode=DISABLED`; do not copy that shape to production.
- Targeted test: load `CONNEX_DB_*` from your untracked `backend/.env`, then run `./gradlew test --tests '<fully.qualified.TestClass>'`. Add selectors for directly affected guard or integration tests.
- Compile/package without the exhaustive suite: `./gradlew assemble testClasses`
- Full backend suite: CI-owned through `Backend — build & test`. Do not run bare `./gradlew test` or `./gradlew build` on the shared development host except under the root execution-discipline exceptions.
- Seed fixture: run `./gradlew seedData -PseederProfile=small -PseederSeed=853 -PseederAnchorDate=2026-01-15` only against a fresh disposable schema whose catalog starts with `connex_seed` or `cnx_seeder_`. The task uses the production runtime classpath, excludes DevTools and its home-directory overrides, protects both `connexdb` and `connex_pub`, requires a numeric loopback address for local use, always refuses textual `localhost`, requires explicit confirmation for any other host, refuses auto-configuration exclusions, revalidates after every environment post-processor, checks the server-reported current database, and requires Flyway to report the complete current migration set before fixture writes; see [`../docs/VOLUME_SEEDER.md`](../docs/VOLUME_SEEDER.md)
- DB up: create `backend/.env` from `backend/.env.example`, fill local-only passwords, then run `docker compose up -d db` (from `backend/`)
- Private uploads (local): the default root is `~/.connex/object-storage`; override it with `CONNEX_OBJECT_STORAGE_FILESYSTEM_ROOT` when tests or parallel worktrees need isolation.
- OCR up: set a unique local `CONNEX_OCR_SERVICE_TOKEN` in `backend/.env`, then run `docker compose --profile ocr up -d ocr` (from `backend/`); see `../ocr/AGENTS.md` for model, test, benchmark, and resource rules
- Routing integration test: `TenantCatalogRoutingIntegrationTest` creates a scratch catalog `connexdb_routing_it`; when the test DB user lacks the privilege (CI runs as root and has it) the test self-skips with instructions. To run it locally, grant once as root: ``GRANT ALL PRIVILEGES ON `connexdb\_routing\_%`.* TO 'connexuser'@'%';``
